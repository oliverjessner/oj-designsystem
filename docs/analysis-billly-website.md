## Billly

### Existing tokens and visual language

`src/styles.css:1–36` defines a dark theme with `--bg: #0f1014`, `--bg-soft: #151824`, `--panel: #191c2b`, `--panel-2: #202436`, `--text: #f3f4f6`, `--muted: #9aa3b2`, magenta `--accent: #d946ef`, orange `--accent-2: #ff7a59`, and independent success, warning and danger colors. Typography comes from externally hosted Space Grotesk. Panels use 18px radii; controls use 10–12px radii; several controls use fully rounded pills. Gradients, bright shadows and a glowing status dot are present. These are consumer-specific historical styles, not the requested visual target: BulkPixel's calmer geometry must lead the shared system.

### Inconsistencies to resolve

- Main view buttons switch `.active` classes on click without a tab/tabpanel relationship, roving tabindex or Arrow/Home/End key handling. The shared tabs behavior must implement those semantics explicitly.
- Email/settings rows declare `role="tablist"`, but their buttons do not provide a complete tabs contract. Exclusive data filters must remain separate from panel navigation.
- Focus styling differs between magenta status choices and hardcoded blue form controls (`src/styles.css:1285`). It should use a single theme-independent visible focus token with tested contrast.
- Small uppercase 11px labels and 13px table text require direct Comfortaa readability checks; do not mechanically retain Space Grotesk sizing.
- Public CSS/data names are unnamespaced; replacing them requires an explicit future consumer migration, not aliases leaking into the new library.
- Table rows are click targets; row styling does not supply keyboard interaction. Consumers should use a real button/link within the row rather than relying on mouse-only row handlers.
- Gradients, glow, repeated pills and large panel shadows contradict the requested quiet shared identity and should not be copied.

## oliverjessner.at

### Existing foundations

`_data/site.json` and deployed `/assets/css/main.css` agree: the shared site shell uses black `#000000`, secondary surface `#1d2026`, stronger surface `#24272d`, primary text `#F4F4F5`, muted text `#D1D5DB`, and current red accent `#FF4A4A`. The requested purple `#7d34c5` is a future product override, not an observed current value. Body/logo use Comfortaa, headings use Lato, and code uses Fira Mono, all loaded through Google Fonts in `_layouts/default.html`. The new library should ship Comfortaa and JetBrains Mono locally and remove the need for heading-specific third-party font identity.

Website CSS is modular but combines Bootstrap-style layout/vendor rules, global reset/type rules, component rules and page-specific CSS through `assets/css/main.css`. Global body text is 18px; `.content` is 19px with paragraph leading 1.56. Prose needs a readable, looser context alongside the compact desktop control scale.

### Inconsistencies to resolve

- Current general headings use a separate Lato family despite Comfortaa being the body identity. New token typography should stay consistent without reducing article readability.
- Global list reset hides bullets, then `.content` restores them. The library should scope editorial styling and avoid consumer-wide aggressive list resets.
- Cards vary between 20px rounding, zero card radius, image saturation/zoom effects and editorial borders. Retain the information hierarchy, not those inconsistent decorative treatments.
- Article tables use vertical borders and a strong accent hover even for static content; shared table defaults should use subtle horizontal separation and reserve pronounced hover for actual interaction.
- Existing pagination emits unlabeled icon-only previous/next links and marks active items through class alone. The new example/API must include accessible names and `aria-current`.
- Older contact form include resets the submit button outline and embeds component-specific CSS. It is source evidence only; the current contact page does not render it. New fields and buttons should keep visible keyboard focus.
- The shared website shell and standalone product pages differ in structure. Do not force a single landing-page layout into the package.

## Extraction decision

The strongest overlap between Billly, the website and the tool suite is typography/tokens, labeled native forms, buttons with icons, panels/cards, wrapping toolbars/navigation, tables, tags/status, metrics and code/technical text. Website prose, card metadata and site header/footer are generic optional components. Sorting, routing, search indexing, invoice intelligence, email sending, billing, content/schema generation and concrete consumer layouts remain consumer responsibilities.

Migration should replace foundations and leaf controls first, then audited interactive contracts. This avoids importing Billly's business logic or the website's Bootstrap/layout/template architecture into the framework-independent library.
